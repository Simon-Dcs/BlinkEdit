## 已批准的实验目标与约束

以下保留执行前的目标和方法；实际完成程度以上述结果与完整报告为准。

## 1. 实验目标

以 RoboDojo 的 `deposit_coin` 为一个小规模案例，检验 **EmbodiedGen 本身的 GPT 驱动场景生成、编辑、检查与可视化能力**：

1. 将一个固定的 `deposit_coin` 场景及其依赖复制到 **EmbodiedGen 仓库内的独立实验目录**。
2. 使用 EmbodiedGen 的现有模块、CLI 和 skills，把硬币和存钱罐的投币口都变大。
3. 保存原始基线与每一轮编辑后的完整场景、同视角图片、视频和检查结果，让用户看清每轮改变了什么。
4. 记录每轮以及整体的真实耗时、GPT token 用量、失败和重试。

这里的“复制到本文件中”按“复制到本仓库的实验目录”执行：本 Markdown 文件保存方案，场景及二进制资产另存。

**复现的主体必须是 EmbodiedGen。** 当前助手负责环境准备、调用项目接口、观察输出和整理结果；不能由 Codex 另写一套建模脚本把场景改好，再称为 EmbodiedGen 的复现。此次也不扩大为论文全部指标复现或机器人策略训练。

## 2. GPT 的角色与接入方式

GPT 应通过项目的 `GPT_CLIENT` 参与所需的规划、描述、语义理解或视觉检查；生成、变换、场景装配与渲染由 EmbodiedGen 对应模块执行。保存实际调用链，区分“项目原生调用”“实验编排”和“格式适配”。

**已确认使用 ChatGPT 订阅账号，经项目已有 `GPT_CLIENT → codex exec` 后端接入；不使用 GPT API 或 API Key。** 该后端仅承担库所需的语言/视觉请求，不允许外层 Codex 绕过库完成目标几何编辑。实验使用显式模型与独立用量日志，避免沿用 YAML 的 Azure 默认配置。

执行中，**都不允许用外层编码 agent 替代 EmbodiedGen 的核心能力**。实际模型、provider、参数和使用范围必须写入实验记录。

## 3. 已定位的源文件与基线

优先使用以下固定场景，避免每轮随机生成不同布局：

```text
/data2/dcs/RoboDojo/Assets/Eval_Layout/RoboDojo/arx_x5/0/deposit_coin_0.json
```

关联的任务与主要资产：

```text
/data2/dcs/RoboDojo/task/RoboDojo/tasks/deposit_coin.py
/data2/dcs/RoboDojo/task/RoboDojo/config/deposit_coin.yml
/data2/dcs/RoboDojo/Assets/Object/RoboDojo/Rigid/coin/00000/
/data2/dcs/RoboDojo/Assets/Object/RoboDojo/Geometry/piggy_bank/00000/
/data2/dcs/RoboDojo/Assets/Object/RoboDojo/Geometry/vertical_coin_stand/
```

任务语义是从支架取出硬币，投入存钱罐。复制时还需要追踪桌面、房间、材质等实际依赖，不能只复制布局 JSON。

注意两个已经发现的细节：

- RoboDojo 的 `Assets` 是指向 `.cache/robodojo_assets_repo/Assets` 的符号链接。复制必须落实为实验目录中的独立文件，不能保留指向源资产的可写链接或使用硬链接。
- 硬币元数据的 `geometry.aligned_bbox.extents` 为 `[0.0285, 0.0285, 0.0019]`，而布局及 `physics.size` 为 `[0.0209, 0.0209, 0.001]`。执行时需要核对 USD 单位、变换及加载缩放，测量最终生效尺寸，不能任选一组数字作为真值。`slot_opening` 功能点也不是投币口尺寸。

## 4. 原场景保护与实验目录

**禁止修改 `/data2/dcs/RoboDojo/` 下的原场景、资产、配置、任务代码及其符号链接指向的真实文件。** 不向原目录写入渲染缓存、转换结果或日志，也不修改其全局资产根配置。

执行后的文件集中放在：

每轮从上一轮的独立副本继续，保留全部历史结果；不用工具的覆盖行为丢掉上一轮。所有可变资产引用均指向本次实验目录，运行前检查解析后的真实路径。已有实验目录不覆盖。

## 5. 先验证库的能力，再决定具体编辑路线

已阅读本地 `README.md`、Vibe Coding 文档及相关 skills。当前明确的能力包括：

- `asset-process`：URDF 资产的**整体等比缩放和旋转**，同步处理支持的视觉与碰撞文件。
- `spatial-computing`：实例查询、放置、插入、删除及碰撞感知布局。
- `img3d-cli` / `text3d-cli`：通过项目后端生成资产。
- `sim-cli`：对项目支持的布局进行 SAPIEN 仿真渲染。

**两个关键适配点尚未验证：**

1. RoboDojo 当前资产是 USDZ，布局也不是 EmbodiedGen 的 `layout.json`。需要验证能否保真导入项目所需格式，保留单位、位姿、材质、碰撞结构和功能点。适配可以转换格式，不能顺手完成目标几何编辑。
2. 上述已读接口没有提供明确的“保持罐身不变，只扩大投币口”的局部拓扑编辑能力。整体放大存钱罐不等同于完成要求；把槽口涂黑或修改纹理也不算扩大真实开口。

执行时先核实是否还有可复用的原生接口。若只有资产再生成/替换路线，需先说明它可能改变罐身外观，并由用户确认后再作为该路线继续；不能称为原资产的精确局部编辑。若项目确实不支持目标操作，记录已完成的轮次与能力缺口，提交“授权扩展库”或“调整为库原生支持的简单任务”的具体建议，**不私自改题、不手工建模绕过问题**。

## 6. 逐轮实验与预期视觉变化

默认采用一个场景、固定种子、小规模串行执行。以下倍率是本方案的建议值，批准后以实测基线为参照执行。

### R00：未编辑基线

- 加载独立副本并完成必要格式适配，不改变对象尺寸和布局。
- 对比源场景副本与适配结果，确认没有把转换误差当作编辑效果。
- 记录硬币直径/厚度、投币口长度/宽度、罐身尺寸，统一保存为米并在图表中标注毫米。
- 保存全景、硬币特写、槽口特写和基线短视频。

### R01：放大硬币

- 建议硬币整体等比放大到基线的 **1.5 倍**，直径和厚度均随之变化，优先使用 `asset-process`。
- 暂不扩大投币口，使这一轮的变化单独可见；此轮可能尚不能完成投币，照实记录。
- 检查视觉网格、碰撞几何、支架接触和物理参数是否一致。支架如无法容纳新硬币，先报告所需的最小适配，不擅自删除支架或把硬币移到桌上。
- 记录 GPT 在本轮实际承担的理解/检查工作，以及库工具真正执行的变换。

### R02：放大投币口

- 保留 R01 的大硬币，扩大真实槽口的长度和宽度；尽量保持罐身尺寸、颜色、位置及其他场景元素不变。
- 建议槽口长宽均至少达到基线的 **1.5 倍**，同时按硬币插入方向检查新直径、厚度和通行余量；最终尺寸及余量在执行前量化记录。
- 必须同时检查可见开口和碰撞通道，不能出现“图片上有孔，但碰撞壳封死”的结果。
- 若第 5 节的局部编辑能力缺口不能解决，本轮标为未完成，保留证据，不制造成功截图。

### R03 及后续：仅做有依据的修正

- 根据前一轮渲染、几何测量和碰撞检查，修正具体问题；每轮写清原因、输入指令、调用模块和结果。
- 默认最多追加 **2 轮**修正，避免无上限重试；仍未满足要求则报告剩余问题和所需决策。
- 所有失败尝试计入时间与 token，并保留能生成的视觉结果；加载失败则保存错误和失败资产，不冒用上一轮图片。

每轮固定保存相机位姿、焦距/视场角、分辨率、灯光和对象位姿。展示顺序为 **R00 → R01 → R02 → 修正轮次**，不能通过移动相机或改变缩放制造“变大”的视觉效果。

## 7. 可视化与完成判据

每轮至少交付：全景 PNG、硬币与投币口的同视角近景、尺寸记录、场景/资产快照、执行日志。最终提供横向对照图、逐轮切换 GIF 或 MP4，以及最终场景视频；图片来自实际资产渲染，不使用生成示意图冒充实验输出。

完成要求：

1. 能从日志与产物追溯 EmbodiedGen 和 GPT 各自的实际贡献，而非只展示手工修改结果。
2. 硬币与真实投币口均比基线大，图像对照和数值测量一致。
3. 视觉与碰撞结构一致，场景可加载；通过受控的对齐、低速插入/落入检查验证通行，而不是只观察一张图。
4. 不改变原任务的成功定义来迁就结果。RoboDojo 原任务还要求机器人返回原位；本次几何通行检查不等同于机器人完整任务成功，也不宣称策略成功率提升。
5. RoboDojo 原始文件保持不变，每轮记录完整，能按保存的配置重跑。

若渲染、真实开口编辑或通行验证未完成，报告中明确标注未达成项及原因，不将局部结果写成整个任务完成。

## 8. 耗时与 token 的记录口径

### 耗时

- 记录开始/结束时间、时区及单调时钟测得的秒数。
- 分开记录环境准备/首次下载、格式转换、GPT 请求、资产生成或编辑、验证、渲染以及整轮墙钟时间。
- 汇总“包含准备的总耗时”和“准备完成后的实验耗时”；失败、重试和模型等待均纳入。
- 等待用户确认的时间单列，不混作模型推理时间；并发阶段不简单相加冒充墙钟时间。

### Token

- 每次真实模型调用保存 `round_id`、阶段、调用模块、provider、实际模型、请求标识、尝试序号、状态、耗时和后端原始 `usage`。
- 统计输入、输出、总 token；后端提供缓存或 reasoning 明细时保留，注明它们是否已经包含在总数中，避免重复相加。
- 计入规划、视觉检查、纠错和重试。纯几何/渲染步骤若没有调用 LLM，记录为不适用，不伪造 token 用量。
- 当前 `GPTclient.query()` 只返回文本，未保存响应 `usage`；实验前需在请求边界增加最小计量记录，保持原有调用接口及行为，不凭输出字数反推精确 token。
- 请求失败且未返回 usage 时记为“未知”，不能当作 0；汇总报告同时给出已知用量和未知请求数量。
- 当前聊天助手的编排用量与库内部 GPT 调用分列。若运行环境不提供当前聊天的精确 token，明确写“不可获取”，不把库内用量称为全部 agent 用量。
- 若用户选择订阅/Codex 后端，先验证其用量事件是否可采集；不能仅因拿到最终回复就声称 token 已完整统计。

所有 prompt、响应、命令和错误日志应足以重放实验，但不保存 API Key、登录令牌或认证文件。

## 9. 用户确认后的执行顺序

1. 按第 2 节已确认的订阅方式接入；记录实际仓库版本、依赖与可用计算资源，不因 README 的示例命令直接切换分支或重装现有环境。
2. 建立独立副本和资产映射，验证格式适配及局部槽口编辑的原生能力；先处理影响路线的真实缺口。
3. 建立耗时与 token 记录，再开始模型请求；记录必要环境准备开销。
4. 依次执行基线、编辑、逐轮渲染和检查，按证据决定是否修正。
5. 交付对照图/视频、最终可加载场景、逐轮记录、总耗时与 token 汇总，以及最小复跑命令。
