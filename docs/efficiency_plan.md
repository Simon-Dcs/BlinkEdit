# EmbodiedGen 3D Editing 效率优化实验计划

**版本：2026-11-14 · 状态：待审阅，尚未启动新实验。**

## 1. 本轮要回答什么

在保持编辑质量和任务含义不变的条件下，降低：

1. **从完整自然语言需求到验收完成的总 token**，包括规划、纠错、失败与重试。
2. **同一完整过程的墙钟时间**，包括场景读取、模型等待、编辑、检查和最终预览。

推荐路线：**一次规划 + 精确 ID + 原生批量执行**；在此基础上验证精简上下文、跨轮状态复用和常驻进程的增量收益。

本次先做小规模、可归因的对照，不同时更换模型、GPU、几何算法或生成后端。所有场景修改继续调用 EmbodiedGen 原生接口。

### 一个重要的基线选择

上一轮的 E1 **已经实现了“一次 GPT 规划 + 原生批量执行”**，平均 28.09 秒、15,725 tokens，完成一次删除加四个插入。不能把这项已有收益再次包装成新优化，也不能故意增加模型调用来制造更慢的基线。

因此：

- **主基线使用 E1 的完整指令流程。** 所有主实验都接收完整自然语言，不提前提供正确对象 ID 或正确编辑计划。
- 上一轮 H1 用于说明重复语义调用的成本；它与 E1 工作量不同，不能直接作为新实验的配对收益。
- **A1/A2 只保留在瓶颈诊断附录**，不作为完整任务的零 token 方案，也不默认重跑。

已有证据见 [efficiency.md](efficiency.md) 和 [上一轮原始汇总](outputs/efficiency/20261112_214800/metrics/summary.json)。

## 2. 优化项、假设与预期

| 优化项 | 准备验证的改动 | 主要影响 | 预期与风险 |
|---|---|---|---|
| P1 精简规划上下文 | 用紧凑的当前场景状态、已确认指代和必要历史替代重复信息；计划仍一次生成 | 总 input tokens，可能影响模型延迟 | 单轮小场景收益可能很小；连续编辑更值得测试。不能省略消歧所需信息 |
| P2 常驻本地执行进程 | 复用 Python 导入、原生执行器与 SAPIEN 渲染器；模型后端调用方式不变 | 导入、初始化和预览耗时 | 上轮独立验证导入约 5–6 秒，有明确优化空间；必须防止旧场景残留 |
| P3 组合 | 只组合已经通过检查的 P1/P2 | 总 token 和总延迟 | 验证组合后仍然正确，不直接把单项收益相加 |

**关于缓存的具体含义：** 缓存已经确认的实例 ID、房间归属、上轮操作结果和必要指代关系；每轮仍以实际场景为准。它不是预存测试题答案，也不是把上次完整计划原样执行一遍。

新的自然语言指令仍交给 GPT 解析。**复用 ID 并不自动意味着可以省掉这一轮模型调用。** 相对已经只有一次规划调用的 E1，P1 主要减少重复输入，而不是预期从一次调用变成零次。

上一轮检查本来就是程序性检查，没有逐次调用 GPT 看图。因此本轮继续使用程序检查，不能把“取消原本不存在的 GPT 检查”算作收益。只有需要重新理解目标或修正计划的异常才进入模型纠错。

### 暂不实施的方向

- 更换模型或降低 reasoning effort：会引入质量与模型能力变量，先固定 `gpt-6-astra / medium`。
- 更换 GPU：此前主要瓶颈在模型往返和进程开销。
- 修改原生碰撞搜索、网格采样或资产几何：本轮先优化编排与运行方式。
- 接入新的付费 API、非公开端点或提取登录凭据：继续使用项目原生 Codex 订阅后端。

## 3. 实验组：每组都包含语言理解和最终检查

| 组别 | 规划输入 | 本地执行方式 | 与谁比较、回答什么 |
|---|---|---|---|
| M0 主基线 | E1 风格的场景清单与完整指令；连续会话附必要的先前指令和已确认结果 | 每次新建执行/验证进程；一次规划后原生批量执行 | 当前完整工作流的真实成本 |
| M1 上下文优化 | 同一事实集合，紧凑结构化表示；复用有效指代，删除冗余历史 | 与 M0 相同 | M1↔M0：单独测输入组织与缓存的影响 |
| M2 常驻进程 | 与 M0 相同的提示词和信息 | 复用本地进程、执行器及渲染器 | M2↔M0：单独测启动与状态复用的影响 |
| M3 组合候选 | 采用通过验证的 M1 方案 | 采用通过验证的 M2 方案 | 与同任务 M0 比较最终增量收益 |

两组对照接收相同自然语言、相同起始场景和资产目录，使用相同输出要求、检查方法、搜索预算与纠错上限。**预期答案只进入验收器，不进入规划 prompt 或缓存。**

M0 不发送完整控制台日志、图片 base64 或无关历史来人为扩大 token。M1 的信息压缩使用确定性代码；如果执行时确实需要额外模型摘要，其耗时和 token 必须计入 M1。

M2 只让本地代码常驻，不在本轮改变 `GPT_CLIENT → codex exec` 的认证或模型会话机制。连续请求之间保留可追踪的场景状态；切换独立任务时必须清除前一任务的场景对象。

### 共用的最小执行协议

实施时在实验编排层统一“可执行计划 / 需澄清 / 无法完成”的结果格式，以及计划检查和错误记录。两边共用相同协议，不把协议修复只加到优化组。

所有动作先验证合法性，再在独立候选场景中调用原生编辑接口；通过本轮约定检查后才发布结果。部分成功、剩余失败要有明确状态，不能把原生批量接口的部分写回当成整条指令成功。这些副本和检查开销也计入总耗时。

这里的完整指令适配、上下文压缩与进程复用都是**实验侧编排改动**；原生生成/编辑能力与新增编排能力分别标注。若需要修复原生状态同步缺陷，先保留最小复现，并将该修复作为独立改动与基线共同核验，不悄悄更换核心算法。

## 4. 场景、任务与样本安排

### 4.1 复用现有素材，避免混入生成成本

使用上一轮官方 table、lamp、vase、book、mug 资产和双房间输入夹具，素材版本与出处沿用 [manifest](outputs/efficiency/20261112_214800/manifest.json)。每次独立任务从新副本开始；连续会话从各自同一基线开始，后续轮次接续各组实际输出。

本轮测量对象仍是场景级实例编辑，不增加图生 3D、纹理生成、USD 导出或整屋生成。素材准备、输入副本和环境初始化另有计时，不混进模型推理时间。

### 4.2 单轮主任务：4 类 × 3 次 × 2 组 = 24 次

先比较 M0/M1，输入文本提前冻结。

| 任务 | 完整自然语言需求 | 验收重点 |
|---|---|---|
| T1 简单删除 | 删除办公室里的台灯，餐厅保持不变 | 只删除目标对象，不误删另一房间台灯 |
| T2 简单插入 | 在办公室的桌子上放一个花瓶，其他东西不要移动 | 正确支撑面、碰撞网格、保留原有位姿 |
| T3 多对象插入 | 在办公室桌上放台灯、花瓶、书和杯子，不要相互重叠，餐厅保持不变 | 四种资产齐全、避碰、目标房间正确 |
| T4 混合编辑 | 移除办公室地上的台灯，再在办公室桌上放台灯、花瓶、书和杯子，不要相互重叠，餐厅保持不变 | 删除和插入都完成，无部分成功冒充整体成功 |

T3/T4 是本轮相对复杂任务；它们衡量多动作、约束和状态保持，不代表整屋重规划难度。

### 4.3 连续编辑：1 个四轮会话 × 3 次 × 2 组 = 24 轮

比较 M0/M1，双方都可以访问相同的历史事实；差别只在是否精简与结构化复用。

1. “在办公室桌上放一个杯子。”
2. “在刚才那张桌子上再放一本书，保留杯子。”
3. “删掉刚才放的杯子，书不要动。”
4. “再删掉刚才那个杯子。”

第四轮预期是报告对象已经不存在、保持场景不变；不能使用过期绑定删除其他物体。记录首次建立状态的全部成本，以及后续各轮成本和整个会话总成本。不能只挑缓存命中的快轮次展示。

应用缓存遇到删除、改名、跨房间移动、支撑物改变或外部场景更新时必须重新检查。会话开始时缓存为空；缓存建立与维护开销属于优化组。

### 4.4 常驻进程：T3/T4 × 3 次 = 6 次新增实验

测 M2；与 M0/M1 的 T3/T4 安排在同一交错执行区组，复用该区组的 M0 数据，不在数小时后另跑 M2 再直接对比早先的模型延迟。分开报告：

- 首次请求：包括启动、导入、渲染器初始化和加载输入。
- 后续请求：从收到指令到完整检查结束。
- 整段会话：启动成本加全部请求耗时，再计算每任务摊销值。

独立任务的输入加载/重置不能移到计时区间之外。常驻模型客户端不在本阶段范围内。

交错调度中等待其他组的时间单列。摊销值使用初始化、本组请求与重置的实测耗时之和；另保留进程存续墙钟，不把阶段和称作一段无间隙的端到端墙钟。

### 4.5 边界与失败：3 类 × 2 组 = 6 次

使用 M0 和当时最有希望的优化候选，检查一次有意义的反例，而不是无限重复。

| 边界任务 | 预期处理 |
|---|---|
| 固定方向把超尺寸沙发放到办公室桌上 | 拒绝无法满足的放置，不缩放沙发或扩大桌子来偷偷改题 |
| 删除一个场景中不存在的对象 | 报告未找到，保留全部已有对象 |
| 场景中两张桌子都可能匹配，只要求“把花瓶放在那张桌上”，且没有先前指代 | 请求澄清，不任意选一张桌子 |

正确拒绝/澄清与编辑成功分开统计，不把它们合并成虚高的编辑成功率。发生澄清时，计至返回澄清问题，用户等待时间不混入运行耗时。

### 4.6 组合确认与总规模

若 P1/P2 都有价值，追加 M3 在 T3/T4 上各 3 次，并在同一新区组各跑 3 次 M0，共 12 次。这组同期对照用于区分组合收益与远端延迟变化。若只有一项有效，就采用该项，不机械组合。

- 正式基础规模：24 + 24 + 6 + 6 = **60 个单轮任务/会话轮次**。
- 组合确认及其同期基线：最多 **12 次**。
- 计量与协议试跑：最多 **6 次**，单列为工程试跑，仍记录全部消耗。
- 本轮最多 **78 个计时轮次**；一个轮次可能包含纠错请求，模型请求上限见第 8 节。

若更改任务、prompt、协议或算法，之前数据标记为旧版本，不与新版本均值混合；不在看到结果后挑选更有利的任务。

## 5. 计时和 token 怎样记录

### 5.1 两个时间终点，主结果使用验收终点

**起点：** 启动冷流程前收到完整指令，或常驻流程收到完整指令时；首次初始化按冷/热口径如实计入。

- `T_edit`：原生编辑与资产写回完成，URDF 和 floorplan 就绪。
- **`T_verified`：主指标。** 在 `T_edit` 之后，规定的资产/几何检查、SAPIEN 加载、同视角两张预览及适用的支撑诊断都完成，并返回完成/失败状态。

这次直接连续测量 `T_verified`，不再把两个独立进程的历史均值相加当作端到端实测。所有组使用相同的验收终点和画面分辨率。

记录以下阶段的单调时钟起止与 exclusive/inclusive 时间：

1. 初始化与输入副本/状态恢复；
2. 场景读取与上下文构建；
3. 规划模型往返；
4. 计划合法性检查与必要纠错；
5. 原生几何编辑、碰撞搜索、文件复制和写回；
6. 结果检查、模拟器加载、渲染；
7. 失败恢复或回滚；
8. 整体墙钟和进程其余开销。

模型往返包含 CLI、网络、远端等待及计算；没有服务端时钟时不宣称测得纯模型推理时间。嵌套阶段避免重复累计。

### 5.2 总 token 覆盖完整链路

逐请求保存 `task_id / session_id / turn_id / condition / stage / attempt / model / status / latency / raw_usage`，并保存实际 prompt、结构化计划、错误与返回文本。

```text
任务总 token = 所有规划、语义补充、摘要、纠错及失败请求的
             Σ(input_tokens + output_tokens)
```

- input 内已经包含 cached input；另列 cached、uncached、reasoning 明细，不重复相加。
- 使用后端真实 usage，不从字数估算精确 token。
- 失败请求未返回 usage 时记为未知，并单列未知请求数；该组不能宣称总 token 已完整测得。
- 程序性检查没有 LLM 调用则为 0 tokens，但其时间仍计入 `T_verified`。
- 当前监督聊天用量若仍无法获取，明确排除；不能称为整个聊天账号总消耗。
- 订阅 token 不换算成 API 美元费用。

## 6. 怎样保证“更快”不是“少做了事情”

### 6.1 固定实验条件

执行前记录仓库版本、实验脚本版本、Conda 包、Codex CLI 和实际模型配置。复用现有环境；计划使用 GPU 7、`gpt-6-astra / medium`、项目原生 Codex 后端。若执行时模型不可用或版本改变，先记录影响，不自动换模型并沿用旧对照。

所有组保持同样的资产、单位、旋转、10,000 点采样、2,000 次搜索上限、渲染分辨率、检查标准及最大纠错次数。独立案例使用基准种子 42、43、44；完整执行顺序和每步种子落盘。

`trimesh==5.1.1` 的原生表面采样不能仅靠 NumPy 全局 seed 保证逐位复现，因此采用匹配起始场景、相同预算和重复测量，不宣称候选点序列完全相同。本轮不为消除随机性而私改原生采样算法。

组别顺序预先随机/交替安排，防止某一组总在远端更快或缓存更热时运行。模型请求串行；实验之间不并行跑渲染来干扰 CPU 对照。机器非独占的事实和其他负载异常单列。应用冷启动与服务端 prompt 缓存分开标记，不声称强制清空了服务端缓存。

### 6.2 相同的质量门槛

每个成功案例都检查：

- 指定对象的类型、数量、房间和支撑关系满足要求；原有非目标对象保持不变。
- URDF 依赖完整，视觉与碰撞文件存在，实际可被 SAPIEN 加载。
- 使用一致的保守几何检查判断范围和重叠；发现接近边界的候选时保存证据，不把二维近似当作完整三维碰撞证明。
- 保存相同相机与分辨率的前后对照图，并检查实际画面。
- 对可行插入案例，在独立诊断场景释放新增物体模拟 2 秒，检查是否留在支撑物上。诊断统一使用原碰撞网格、摩擦 .6/.5、1 mm contact offset 和同一默认密度；预设平移不超过 2 cm、旋转不超过 5°，且仍保持支撑关系。

支撑诊断及其耗时在对照两侧一致；其状态不写回正式 fixed-joint 场景。诊断不扩展为机器人操作成功率验证。视频只需为预先选定的第一轮保存，额外编码耗时另列，不影响两组统一的主验收终点。

原生引擎失败时最多增加 **1 次模型纠错**，且只能在原指令允许范围内重规划；不能换房间、删约束或缩放物体来制造成功。确定不可行、对象不存在或歧义请求，不反复询问到获得想要的答案。

### 6.3 如何判断值得采用

| 改进方向 | 预设判断标准 |
|---|---|
| 上下文优化 P1 | 在连续会话上，包含首轮和失败轮的总 token 至少降低 **10%**，且不出现新增任务失败、误删或过期状态误用；否则记录收益有限或负结果 |
| 常驻进程 P2 | 在 T3/T4 上，计入初始化摊销后的 `T_verified` 至少降低 **15%**，且质量不下降 |
| 组合 P3 | 保留单项收益，组合后仍满足同样质量要求；若新增复杂性却无明显收益，采用较简单的单项方案 |

这些是**工程取舍阈值，不是已取得的结果或统计显著性门槛**。每组 3 次只支持初步判断；报告全部单次值、均值、中位数、范围及配对变化，不报告可靠 p95 或普遍成功率。

速度快但失败更多不算优化。同时给出全部尝试的消耗，以及在成功数非零时的“总消耗 / 成功任务数”，避免只统计成功样本掩盖失败成本。

## 7. 执行顺序与阶段交付

| 阶段 | 执行动作 | 交付与继续条件 |
|---|---|---|
| 0：审批后准备 | 固定任务与验收表；建立新输出目录；实现共用协议、P1/P2 候选和连续计时；最多 6 次试跑 | 原生调用链、usage 与验收结果可追溯，冻结候选后进入正式实验 |
| 1：单轮与速度对照 | M0/M1 的 24 次单轮任务；M2 的 6 次测量穿插在对应 T3/T4 区组中 | 得到单轮 token、冷启动、热请求和摊销时间，确认无状态残留 |
| 2：连续会话与边界 | M0/M1 的 24 轮连续编辑及 6 次边界检查 | 得到会话总成本与缓存正确性结果；P1 无收益则不继续微调 prompt 凑收益 |
| 3：组合确认 | 必要时 6 次 M3 与 6 次同期 M0 配对测量 | 确定最终推荐配置，保留所有失败和退回方案 |
| 4：汇总 | 核对原始 usage、阶段时间、实际场景与统一验收结果 | 输出可复跑方案及“采用/不采用”的明确结论 |

预计工程准备与脚本调整 **1–3 小时**，正式运行 **1–2 小时**，分析整理约 **1 小时**。这是排期估计，实际模型等待、故障恢复及实现时间分别记录；不作为模型性能数据。

由当前执行助手负责实施、计量、视觉检查与汇总，用户负责审阅本计划及范围变化。没有安排额外代理并行运行。

## 8. 资源、停止条件与产物

### 拟申请的执行额度

- 现有 Conda 环境和官方素材；本地 GPU 固定 **7 号卡**，不抢占或终止其他用户进程。
- 使用现有 ChatGPT 订阅，经项目原生 Codex 后端调用。
- 最多 78 个计时轮次；包括纠错、试跑与失败在内，最多 **100 次模型请求**。
- 按此前约 1.5 万 input tokens/请求估算，预留 **100–200 万已知总 tokens**；这是预算估计，不是消耗承诺，也不是费用报价。
- 已知累计 token 达到 **200 万**、请求达到 **100 次**，或正式实验运行达到 **2 小时**，即停止启动下一任务并提交已有结果；在途请求可能使 token 略超过暂停阈值。
- 单模型请求 timeout 180 秒，单任务最长 600 秒。认证失败、订阅限额、连续 3 次模型请求失败或 GPU 7 冲突时暂停受影响部分；不自动改用收费 API 或其他 GPU。

出现原场景污染、缓存导致错误删除或状态串线时，立即停止该候选的性能测量，保留失败快照，修复后重新标记候选版本。不能在错误候选上继续累计“更快”的结果。
